# Проект: бот-агрегатор вакансий

## Что это

Скрипт, который раз в сутки собирает вакансии из нескольких источников, фильтрует их и присылает владельцу одно сообщение в Telegram со списком подходящих вакансий и ссылками.

Пользователь один — владелец проекта. Никакой многопользовательности, регистрации, команд бота и хранения профилей. Бот только отправляет.

## Требования

| Параметр | Значение |
|---|---|
| Время доставки | 09:00 по Москве — вакансии, 10:00 — подработка |
| Формат | сообщение в Telegram со ссылками; подработка — отдельным сообщением |
| География | Нижний Новгород / Нижегородская область **ИЛИ** удалённая работа в любом городе |
| Дедупликация | одна и та же вакансия не приходит дважды, никогда |
| Если ничего не найдено | всё равно прислать сообщение («за сутки ничего нового») — молчание неотличимо от поломки |

## Архитектура

```
sources/           адаптеры, каждый возвращает List[Vacancy]
  hh.py            api.hh.ru — источник закрыт, отключён
  tg_web.py        каналы через веб-превью t.me/s/, без ключей
  sites.py         парсеры сайтов
core/
  models.py        схема Vacancy
  filters.py       гео + стоп-слова + вайтлист
  storage.py       дедупликация
  digest.py        сборка текста сообщения
  sender.py        отправка в Telegram Bot API
main.py            оркестрация
```

Единая схема, к которой каждый адаптер приводит свои данные:

```python
@dataclass
class Vacancy:
    id: str            # sha1 от source + url (или от source + title + company)
    source: str        # "hh" | "tg:hrhubvacancy" | "site:superjob"
    title: str
    company: str | None
    city: str | None
    remote: bool
    url: str
    salary: str | None
    published_at: datetime | None
    raw_text: str      # для телеграм-каналов — весь текст поста
```

Конвейер: `собрать → нормализовать → отфильтровать → отсеять уже виденные → собрать дайджест → отправить → записать новые id в хранилище`.

Запись в хранилище — **только после успешной отправки**. Иначе при падении отправки вакансии будут помечены как показанные и потеряны навсегда.

## Источники

### hh.ru — недоступен, не тратить время

**15 декабря 2025 hh.ru закрыл соискательский API целиком.** `GET /vacancies` отдаёт
`403 forbidden` на любой запрос, включая `per_page=1`, с любым `User-Agent`. Проверено
вживую в августе 2026.

Регистрация приложения на dev.hh.ru проблему не решает: закрыт весь соискательский
контур, а работодательская часть API требует верифицированного аккаунта компании и
предназначена для другого. Открытым остался только справочник `/areas`.

Код адаптера лежит в `sources/hh.py` и отключён в `main.py`. Если hh.ru когда-нибудь
откроет доступ — вернуть источник в `SOURCES`, положить токен в `HH_ACCESS_TOKEN`,
он подхватится заголовком `Authorization: Bearer`.

Дальше — исходный замысел запросов, на случай если источник оживёт.

Два отдельных запроса, результаты объединяются:
1. Нижний Новгород: `area=<id>` — id получить динамически из `https://api.hh.ru/areas`, не хардкодить.
2. Удалёнка: `schedule=remote` без ограничения по региону.

Поисковые запросы (`text=`) — по направлению «оценка и развитие персонала»: оценка персонала, обучение и развитие, T&D, L&D, корпоративный университет, ассессмент, HRBP, HR бизнес-партнёр, развитие персонала, управление талантами, компетенции.

Пагинация: `per_page=100`, идти по `pages`. Брать только опубликованные за последние сутки.

### Telegram-каналы — приоритет 1, основной источник

Основной способ — **веб-превью** `https://t.me/s/<канал>`: обычная HTML-страница
с последними постами, доступная без api_id, session string и вообще без личного
аккаунта. Реализовано в `sources/tg_web.py`.

Разбор страницы: посты в `div.tgme_widget_message` с атрибутом `data-post="канал/номер"`,
текст в `div.tgme_widget_message_text`, дата в `<time datetime>`. Превью отдаёт около
20 последних постов; если канал за сутки написал больше, добираем предыдущие страницы
через `?before=<номер>`.

Ссылка на вакансию — всегда на сам пост (`https://t.me/<канал>/<номер>`). Правило
«первый http-линк в посте» на практике даёт контакт рекрутёра или рекламную метку.

Переносы строк брать только по `<br>`. `get_text("\n")` ставит перенос между всеми
вложенными тегами и разрывает название вакансии на обрывки в местах жирного шрифта.

Ограничение: каналы с отключённым владельцем превью так не читаются — например,
`job_in_hr` отдаёт страницу без постов. Читать их нечем: остаётся только Telethon
с личным аккаунтом, а этот путь закрыт (см. ниже).

### Telethon — отвергнут, не возвращаться

Форма создания приложения на my.telegram.org стабильно отвечает `ERROR` — без
`api_id` и `api_hash` библиотеку не поднять. Перебраны браузеры, приватный режим,
латиница в полях, пустой URL, смена сети — не помогло.

Решение владельца: **вариант закрыт совсем**, время на него не тратить.

Следствия, с которыми проект живёт:

- каналы с отключённым превью (`job_in_hr`) не читаются никогда;
- **чаты не подключаются вообще** — через веб-превью они недоступны в принципе,
  а другого способа нет. Этап «чаты» из плана убран;
- секреты `TG_API_ID`, `TG_API_HASH`, `TG_SESSION_STRING` не нужны.

Отдельно: обычный бот чужие каналы читать не умеет — это ограничение Telegram,
а не нашего кода. Поэтому «завести второго бота» проблему не решает.

Список источников вынесен в `config/channels.yaml`, не в код. Блок `chats`
оставлен как справочный: подключить его нечем.

#### Каналы-ленты — подключены

Чистые ленты вакансий, один пост = одна вакансия, шума мало.

```
HR-направление:      hrhubvacancy, hrhubvacancy300, job_in_hr, work_hr,
                     forhr, HRTech_Jobs, HR_Analytics_Jobs
Общие и руководящие: forchiefs, toplevel_job, horseatwork, rudakovahr,
                     TheyPayWell, vacanciesbest, hmoffice, talentedpeoples
Каналы сообществ:    rff_channel, vacancyCRC, jobs_vacancy_cv
```

#### Чаты — подключить нечем, список справочный

В чатах вакансии перемешаны с обсуждениями, резюме кандидатов и флудом.
Читать их нечем — веб-превью чаты не отдаёт. Список сохранён на случай,
если появится способ.

```
rff_chat, hrkhabcommunity, HRatWork, hr_friends, hr_recrute,
HRclubvacancies, chat_HRAcademy_AleinikMary, helloworldagencyfaq,
ITrecruiters_community
```

Предфильтр по маркерам вакансии, который задумывался для чатов, всё равно
пригодился: он применяется ко всем текстовым источникам, см. раздел «Фильтрация».

#### Не подключать

- `hrhubresume` — канал для публикации резюме, а не вакансий
- `+0ZX7gj_GUEY1ZGIy`, `RabotaInMoskva` — только Москва, гео-фильтр по неструктурированному тексту ненадёжен
- `offervacancy`, `jobforjunior` — стажировки и junior-позиции
- `smmlancer` — SMM и фриланс

### Сайты — приоритет 2

Реализованы в `sources/sites.py`, подключены отдельными источниками в `main.py`:
падение одного не роняет остальные и попадает строкой в дайджест.

**SuperJob — недоступен, не тратить время.** Публичный API отвечает `403` без
ключа приложения, а страницы поиска отдают капчу. Обходить защиту не будем.

**Работа.ру** — нижегородский поддомен `nn.rabota.ru`, поиск по ключевым словам.
Карточки отдаются в HTML: `.vacancy-preview-card__wrapper`, внутри `__title`,
`__salary`, `__company-name`, `__short-description`.

Даты в карточке нет, поэтому окно `days` там не действует — от повторов защищает
хранилище. На первом запуске придёт всё, что висит по запросам, дальше только новое.

В карточке лежит рекламная аннотация без обязанностей, и фильтр по ручному подбору
на ней слеп. Поэтому страницы вакансий догружаются — но **только для прошедших
по направлению**, иначе это шесть десятков лишних запросов в сутки.

**Глобал52** — нижегородский портал, поиска по словам нет, берём общий список
`/vacancy` и отбираем по дате «Обновлено». Год в дате не указан: берём текущий,
а если вышло будущее — значит объявление прошлогоднее. Страница вакансии
структурная: «Вакантная должность», «Организация», «Район», «Зарплата»,
«График работы».

Объём маленький (около двух десятков в сутки), HR-вакансии там редки. Ценность
в том, что это единственный источник, где вакансии действительно нижегородские,
а не удалёнка по всей стране.

Запросы разнесены паузой в 1.5 секунды. Один упавший поисковый запрос не теряет
остальные; если не прошёл ни один — источник считается недоступным.

Каждый парсер оборачивать в try/except: падение одного сайта не должно ронять весь запуск. Ошибку логировать и добавлять строку в конец дайджеста («источник X недоступен»).

**Не включать в бота:** ITGorky, IT52, readyconf.ru — это нетворкинг и мероприятия, а не ленты вакансий.

## Фильтрация

Порядок: похоже ли на вакансию → не резюме → релевантность → не ручной подбор →
гео → стоп-слова → вайтлист-исключение.

Первые два шага добавлены после проверки на живых данных: из 72 постов за сутки
без них в дайджест попадало 14 позиций, почти все — удалённые вакансии Go-разработчиков,
тестировщиков и SMM. С ними остаётся 2, обе по делу.

### Похоже ли на вакансию

Предфильтр по маркерам («вакансия», «ищем», «в команду», «требуется», «обязанности»,
«вилка», «откликнуться» и т.п.) плюс отсев сообщений короче 200 символов.

В списке только однозначные признаки найма. Общие слова оттуда убраны: маркер
«ищет» находился внутри «когда вы ищете новое место» и пропускал редакционную
статью «Корпорация или стартап: как тип компании меняет карьеру в HR».
«Зарплата» и «условия» встречаются в любом тексте про работу.

Отдельно отсекается реклама: подборки каналов, промо и оплаченные посты.
Они содержат маркеры вакансии, потому что так описаны чужие каналы внутри —
подборка «лучшие Telegram-каналы о HR» прошла по слову «резюме». Признаки:
фразы вроде «собрали для вас», пометка `erid`, а также слово «канал» более
двух раз — у настоящей вакансии повода повторить его столько раз нет.
Изначально задумывался только для чатов, но каналы тоже несут рекламу конференций,
промо-посты и личную переписку — применяется ко всем текстовым источникам.
Вакансии без `raw_text` (из API и с сайтов) проходят как есть.

### Не резюме

Часть каналов публикует вакансии и резюме соискателей в одной ленте — например
`jobs_vacancy_cv`. Предфильтр их не различает: «в поиске» и «резюме» встречаются
и там, и там. Отсев по маркерам «нахожусь в поиске работы», «ищу работу»,
«рассматриваю предложения» в начале текста, где соискатели представляются.

### Релевантность

Вакансия должна относиться к направлению. Без этого шага стоп-слова не спасают —
они не знают ничего про Go-разработчиков, а гео пропускает любую удалёнку.

Проверяется **только по названию**. По всему тексту поста искать нельзя: почти любая
вакансия упоминает «обучение» и «мотивацию» в разделе условий, и фильтр перестаёт
отсекать что-либо вообще.

Маркеры разделены на два класса:

- **Сильные** однозначно указывают на HR-профессию и срабатывают сами: `hr`,
  `персонал`, `hrbp`, `t&d`, `ассессмент`, `кадровый резерв`, `тренинг`.
- **Слабые** сами по себе не значат ничего и требуют HR-контекста рядом
  (`персонал`, `сотрудник`, `команд`, `руководител`, `кадр`): `развити`, `обучени`,
  `оценк`, `бизнес-партнёр`, `компетенц`.

Причина разделения — реальные ложные срабатывания на двухнедельной выборке:
«ассистент по развитию соцсетей», «эксперт по обучению ИИ», «коммерческий директор
по развитию в театр», «финансовый бизнес-партнёр в банк».

Отдельно перечислены сочетания, где слабый маркер сам является профессией:
`специалист обучени`, `менеджер оценк`, `обучени развити` и подобные. Без них
терялся «Специалист по обучению» — целевая вакансия, в названии которой нет
ни слова «персонал», ни «HR».

Итог на живых данных за 14 дней: 670 постов → 508 похожи на вакансию → 60 по
направлению → 21 прошли гео → 7 после стоп-слов.

### Не ручной подбор

Владельцу интересно **руководить** процессом найма и иногда собеседовать точечные
позиции, но не закрывать вакансии руками как основную работу.

По названию это неразличимо: «HR-менеджер» и «Менеджер по персоналу» бывают и
руководителем HR-функции, и рекрутёром на потоке. Поэтому — единственный фильтр,
который смотрит **в текст поста**, а не в название.

Считаются маркеры ручного подбора («полный цикл подбора», «активный поиск»,
«план по набору», «опыт в подборе», «звонков в день», «шорт-лист») и отдельно
маркеры руководства («курировать», «управлять командой», «выстроить процессы
с нуля», «аудит», «метрики»). Вакансия отсеивается, если маркеров подбора больше
одного, а признаков руководства меньше двух.

Порог выбран по живым данным. У вакансий, забракованных владельцем, маркеров
подбора 2–9; у оставленных — «Head of HR / HRD» и «HR Director» — ни одного,
при 4 и 8 признаках руководства соответственно.

Фильтр отсекает много: из 671 поста за две недели после него остаётся 2 вакансии
вместо 7. Это цена узкой специализации, а не поломка.

### Гео
Пропускать, если город = Нижний Новгород / Нижегородская область, **или** вакансия помечена как удалённая.

Правило строгое и обсуждению не подлежит. Проверка за две недели показала, что
оно стоит дорого: в отсев попала «Руководитель управления оценки персонала»
(компания «А7», дочерняя ПСБ) — самая точная по профилю вакансия за период,
без единого маркера ручного подбора. Отсеялась из-за пометки «офис, Москва».

Предлагалось добавить в конец дайджеста справочный блок «по профилю, но не
по гео». **Владелец отклонил:** гео — чётко Нижний Новгород или удалёнка.
Не возвращаться к этому и не смягчать фильтр «ради полноты картины».

### Стоп-слова
Проверяются **по названию вакансии**, регистронезависимо, по вхождению основы слова
**от начала слова**. Без привязки к границе слова короткие латинские основы дают
ложные срабатывания: `hr` находится внутри `through`, а посты бывают на английском. Хранить в `config/stopwords.txt`, одна основа на строку. Использовать основы, а не полные формы: `охран` вместо `охрана`, `юрис` вместо `юрист`/`юрисконсульт`, `страхов` вместо трёх вариантов.

```
продаж, аналитик, программист, call-центр, офис-менеджер, секретар,
транспорт, страхов, курьер, сборщик, продавец, администратор, диспетчер,
кладовщик, повар, педагог, клиентск, помощник, строительн, участок,
техническ, водител, инженер, бухгалтер, юрис, станков, технолог, сварщик,
крановщик, мастер, экономист, прораб, охран, рекрутер, найм, подбор,
закупк, смена, монтаж, взыскан, швея, хостес, официант, груз, заведующ,
бригадир, комплектовщик, персональн, доставк, маркетолог
```

### Вайтлист-исключение

Стоп-слово **не отсеивает** вакансию, если в названии одновременно есть один из целевых маркеров:

```
оценк, развити, обучени, T&D, L&D, talent, HRBP, бизнес-партнёр,
корпоративн университет, ассессмент, assessment, компетенц, адаптаци,
кадровый резерв, performance
```

Причина: без этого правила отсекаются релевантные вакансии вроде «Аналитик по оценке персонала», «Руководитель отдела персонала (подбор и развитие)», «Мастер производственного обучения».

## Подработка — второй поток

Владелец ищет подработку, пока не найдено основное место. Это **отдельное
сообщение** со своими источниками и своими фильтрами: `core/gig_filters.py`.

Логика обратная основному поиску. Там отбор узкий — вакансия должна быть про
оценку и развитие персонала. Здесь сеть широкая: отсекаем только явные «нет»,
остальное показываем списком. Причина — подработку выбирают по обстоятельствам,
и строгий фильтр потеряет больше, чем сэкономит.

### Что подходит

Удалённая частичная занятость любого толка (обработка данных, кураторство,
модерация), разовые проекты по профилю (тренинги, ассессмент, деловые игры),
квизы и викторины, подкасты и несложное ведение мероприятий в Нижнем Новгороде,
а также простая офлайн-работа рядом с домом.

### Что не подходит

Список собран из прямых оценок владельца на живой выдаче, менять его без
спроса нельзя. Граница тонкая и логикой не выводится:

| Подходит | Не подходит |
|---|---|
| расклейщик | промоутер |

### Гео подработки — строже основного

Удалённая — откуда угодно. Офлайн — **только рядом с домом**: Анкудиновка,
Новая Кузнечиха, ЖК Цветы, улицы Богородского и Медицинская. Обычная Кузнечиха,
Советский район целиком, Щербинки, Верхние Печёры и Тропинина исключены
владельцем сознательно.

Два подвоха, из-за которых нельзя искать по простому вхождению:

- «Новая Кузнечиха» содержит внутри «Кузнечиха», а её владелец исключил, —
  поэтому ищется словосочетание целиком;
- названия улиц ищутся только рядом со словом «улица»: иначе «медицинская»
  ловит «медицинскую книжку», которая есть в каждом втором объявлении.

### Источники подработки

- **FL.ru** (`sources/fl.py`) — разовые заказы. Поиск по слову через адрес

содержимое рисуется скриптами; **Хабр Фриланс** закрыт (410).

## Хранилище

SQLite-файл `seen.db` в репозитории, одна таблица:
`id, source, title, url, first_seen_at, fingerprint`.

Вакансия считается виденной по двум признакам:

- **`id`** — sha1 от источника и ссылки: тот же самый пост.
- **`fingerprint`** — sha1 от первых 200 символов нормализованного текста:
  та же вакансия, перепечатанная в другом канале.

Отпечаток нужен потому, что одна вакансия расходится по нескольким каналам почти
дословно. Пример с живых данных: «HR-специалист, DI AUTO TRADING» пришёл из
`jobs_vacancy_cv` и из `work_hr`, отличаясь только строкой `#вакансия_удаленка`
сверху. Поэтому при нормализации выбрасываются хештеги, упоминания и ссылки,
а берётся начало текста — подпись канала обычно дописывают в конец.

Сравнивать по названию **нельзя**: «HR менеджер» в одном и том же канале —
это две разные вакансии у разных компаний, проверено на живых данных.

Дубли схлопываются и внутри одной выдачи, иначе перепечатка пришла бы дважды
в одном сообщении.

GitHub Actions коммитит изменённый файл обратно в репозиторий в конце запуска. Некрасиво, но не требует внешней базы и для одного пользователя работает годами.

Не чистить хранилище по времени — вакансия может висеть месяцами и переопубликовываться.

## Доставка

Telegram Bot API напрямую, без библиотек:

```
POST https://api.telegram.org/bot<TOKEN>/sendMessage
```

- `parse_mode: HTML` — надёжнее Markdown, меньше проблем с экранированием
- Лимит сообщения 4096 символов. Если дайджест длиннее — резать на несколько сообщений по границе вакансии, а не по символам.
- Группировать вакансии по источнику, внутри — по дате публикации.

Формат строки: название ссылкой, компания, город/удалёнка, зарплата если есть.

## Запуск

GitHub Actions, два расписания:

- `0 6 * * *` (06:00 UTC = 09:00 MSK) — основной дайджест;
- `0 7 * * *` (07:00 UTC = 10:00 MSK) — подработка.

Поток выбирается по времени запуска через `github.event.schedule` и
передаётся в `DIGEST_STREAM`. При ручном запуске поток задаётся вводом
`stream`; без него выполняются оба.

Известное поведение: запуски по расписанию в GitHub Actions задерживаются на 5–20 минут при нагрузке. Гарантированной минутной точности нет. Если критично — переезжать на VPS с системным cron.

Обязательно добавить `workflow_dispatch` для ручного запуска при отладке.

Secrets: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

`HH_ACCESS_TOKEN` понадобится, только если hh.ru когда-нибудь откроет доступ.
`TG_API_ID` / `TG_API_HASH` / `TG_SESSION_STRING` не нужны — Telethon отвергнут.

Права workflow в настройках репозитория должны стоять **Read and write**:
по умолчанию GitHub даёт токену только чтение, и шаг с коммитом `seen.db`
падает. Дедупликация при этом ломается молча — вакансии приходят повторно.

Права workflow: `contents: write` — нужны для коммита `seen.db`.

## Тесты

`python tests/test_filters.py` — проверка фильтров на случаях, найденных на живых
данных: целевые вакансии, реальные ложные срабатывания, резюме, статья, отпечатки.

Правило: нашли ошибку фильтра — сначала случай в тест, потом правка. Иначе правило
тихо откатывается следующей же настройкой; так однажды пропал «Специалист
по обучению».

Тест выполняется в GitHub Actions до отправки: ломаный фильтр разошлёт мусор
и пометит его показанным, а вернуть такие вакансии уже нельзя.

## Чего не делать

- Не добавлять команды бота, `/start`-логику, меню, кнопки. Бот только шлёт.
- Не подключать LLM для оценки релевантности на первом этапе — сначала должны работать простые фильтры.
- Не хранить секреты в коде и в конфигах. Только переменные окружения.
- Не делать общий `except: pass` — ошибки источников логировать и показывать в дайджесте.
